## 3. Documents and the _id Field

A Document is a set of key-value pairs. 

```json
{
  "_id": ObjectId("5f46a2b8e3b3c41a2c9f8a3d"),
  "username": "alice",
  "age": 28,
  "hobbies": ["reading", "hiking"],
  "address": {
    "city": "Seattle",
    "zip": "98101"
  }
}
```

### The `_id` Field
Every document in MongoDB **MUST** have an `_id` field. It acts as the Primary Key. 
- It must be unique within the collection.
- If you don't provide an `_id` when inserting a document, MongoDB will automatically generate an `ObjectId` for you.

### What is an ObjectId?
An `ObjectId` is a 12-byte BSON type, represented as a 24-character hex string. It is not just a random string; it contains information:
1. **Timestamp:** The first 4 bytes represent the Unix timestamp when the document was created. *(You don't need a `created_at` field, you can extract it from the ID!)*
2. **Machine/Process info:** The next 5 bytes ensure uniqueness across different servers.
3. **Counter:** The last 3 bytes are a random counter.

Because they are generated using machine info and time, `ObjectId`s can be safely generated by the application (client-side) rather than waiting for the database to assign an auto-incrementing integer.

## 4. Flexible Schema

In a SQL table, every row must have the exact same columns. In MongoDB, documents in the same collection do not need to have the same fields.

**Document 1 in `products`:**
```json
{
  "_id": 1,
  "name": "Laptop",
  "ram": "16GB"
}
```

**Document 2 in `products`:**
```json
{
  "_id": 2,
  "name": "T-Shirt",
  "size": "L",
  "color": "Red"
}
```
This is incredibly powerful for E-commerce catalogs, where forcing laptops and t-shirts into the same rigid table structure would result in hundreds of `NULL` columns.

**Warning:** Flexible schema does NOT mean "no schema". It means the database doesn't enforce the schema. In production, your application code (via tools like Mongoose) should enforce the structure.
